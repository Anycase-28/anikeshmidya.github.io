I work close to the machinery of software: requirements, screens, controllers, stored procedures, APIs, authentication, environments, reports and the people who have to use the thing after it ships.

04 / METHOD

My favourite
feature is clarity.

I have learned that many "coding problems" are actually flow problems: an environment variable, a stale token, the wrong database, an API boundary, an undocumented assumption or a screen that does not match the operator's workflow.

01

Trace before touching.

Follow the request through UI → API → application logic → database. Find where reality diverges from expectation.

02

Keep the contract intact.

Inherited systems have users, dependencies and assumptions. Change deliberately; do not rewrite for sport.

03

Make the invisible visible.

Logs, API documentation, workflow diagrams, training material and useful naming turn hidden system behaviour into something people can reason about.

04

Fix the actual problem.

A green build is not the same thing as a working system. Verify the path that the user actually takes.
